# Maintainer release process

[中文](releasing.md) | [Back to README](../README.en.md)

This guide is only for maintainers with the offline signing key and GitHub release authority, and it must be followed from a complete Git source checkout. The signed release archive retains this process for auditability but does not contain the release-tool source. Users should read [Installation and upgrade](installation.en.md) and [Security and trust model](security.en.md).

## Pre-release constraints

- Root `VERSION` must be exactly one `VERSION="X.Y.Z"` line, with one matching CHANGELOG heading.
- The release commit must be on protected `main`, the worktree must be clean, and the selected CI tier and `ci-gate` must have succeeded.
- An official tag or `--release` build must have the offline GPG private key for the pinned primary fingerprint. The private key must never enter GitHub Actions.
- Official packages always contain amd64, arm64, 386, ppc64le, and s390x; the architecture set cannot be reduced.

## Build signed assets

Complete the gates in [Development and local validation](development.en.md), then run:

```bash
go run ./cmd/sun-release package
cd dist && sha256sum -c security-update-notify-*.tar.gz.sha256
```

An official version must produce and publish exactly four explicit Release assets: the archive, checksum, archive detached signature, and `sun.sh.asc`. The packager immediately verifies its signatures; official tags and `--release` reject `--sign off`.

## Generated files

```text
dist/security-update-notify-VERSION.tar.gz
dist/security-update-notify-VERSION.tar.gz.sha256
dist/security-update-notify-VERSION.tar.gz.asc  # signed build
dist/sun.sh.asc                                  # signed build, high-assurance first install
```

The release archive contains only product files required for installation, diagnostics, bootstrapping, and migration compatibility, plus the user and maintainer guides referenced by the READMEs. Build tools, workflows, and private operations material are excluded. `sun.sh` is included in the signed archive; signed builds also create `sun.sh.asc` outside the archive so nondeterministic signature time never enters the reproducible tarball. The mirror extracts the script and key from the verified archive and publishes them with the detached signature in the immutable version directory; the compatibility stable URL still serves only `sun.sh`. `install.sh` and `files/security-update-notify` are generated by the Go packager as a minimal launcher and version marker for old 2.x self-upgrade clients. They contain no legacy installer/runtime logic and are never installed.

## Publication and mirror protection

The `Mirror signed release` workflow starts after the unprivileged CI for an official GitHub Release completes; that CI is only an event signal and defense-in-depth check and cannot authorize deployment by itself. The actual deployment gate comes from the protected default-branch workflow revision. Its automatic path checks out the successful CI run's fixed `head_sha`, confirms that the tag still resolves to the same commit, then independently verifies the exact asset set, archive, all five ELF identities, static linkage, and every binary's real `--version` with the offline fingerprint and verifier fixed on the default branch. The release tag remains non-executed data throughout. Deployment credentials exist only in a GitHub Environment restricted to `main`, with no repository-level copies; legacy mutable releases can only be repaired manually from `main`. New releases must also contain `sun.sh.asc`, produced by the Go packager with the same offline key and bound to the explicit version. The workflow extracts `sun.sh` and the public key from the verified archive, verifies the bootstrap signature and version notation, and reads the complete versioned set back from `dl.ll.cd` before updating the compatibility stable `sun.sh` and finally `latest.json`. Manually rerunning an older release only repairs that version directory and cannot replace the stable bootstrap or current Latest manifest. Repository Release immutability is enabled; after every successful mirror and each Monday, an independent real GitHub-hosted Ubuntu 22.04/24.04 canary redownloads both public sources and exercises signature verification, installation, doctor, dry-run, timer state, uninstall, and APT-policy restoration.

The Release must first become immutable. After unprivileged release CI verifies the public assets, only the default-branch mirror workflow can use the Environment-scoped deployment identity; the release tag remains unexecuted data. Never bypass checksum, GPG, pinned fingerprint, version notation, five-architecture execution, public read-back, or canary gates.

## Post-release verification

- GitHub Latest points to the target immutable Release, whose explicit asset set contains exactly four files.
- GitHub and versioned-mirror assets are byte-identical and pass checksum and GPG verification.
- Stable `sun.sh`, versioned `sun.sh`, and the signed archive copy match; the critical notation binds the target version.
- Ubuntu 22.04/24.04 public canaries complete install, doctor, dry-run, timer, uninstall, and APT baseline restoration.
- Finally confirm that `main`, its remote commit, the tag, and the published version are bound to the same source.
