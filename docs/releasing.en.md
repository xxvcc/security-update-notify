# Maintainer release process

[中文](releasing.md) | [Back to README](../README.en.md)

This guide is only for maintainers with the offline signing key and GitHub release authority, and it must be followed from a complete Git source checkout. The signed release archive retains this process for auditability but does not contain the release-tool source. Users should read [Installation and upgrade](installation.en.md) and [Security and trust model](security.en.md).

## Pre-release constraints

- Root `VERSION` must be exactly one `VERSION="X.Y.Z"` line, with one matching CHANGELOG heading.
- The release commit must be on protected `main`, the worktree must be clean, and the selected CI tier and `ci-gate` must have succeeded.
- An official tag or `--release` build must have the offline GPG private key for the pinned primary fingerprint. The private key must never enter GitHub Actions.
- Official packages always contain amd64, arm64, 386, ppc64le, and s390x; the architecture set cannot be reduced.

## Build signed assets

Complete the "Validate source changes" gates in [Development and local validation](development.en.md) while
the release worktree is still uncommitted. Commit and push the release commit, wait for protected `ci-gate` to
pass for that exact commit, and then complete the page's "Validate the clean release commit" gate. Create the
annotated tag locally, prepare the variables, and build the official assets; do not push the tag yet:

```bash
set -euo pipefail
tag="vX.Y.Z"
release_sha="$(git rev-parse HEAD)"
git tag -a "$tag" -m "security-update-notify $tag" "$release_sha"
release_dist="$(mktemp -d "/tmp/security-update-notify-${tag}.XXXXXX")"
go run ./cmd/sun-release package --release --sign required \
  --dist "$release_dist" \
  --gpg-key 'C678256ACBFC6491BF5076655F3AE24999921FFC!'
(cd "$release_dist" && sha256sum -c security-update-notify-*.tar.gz.sha256)
```

The trailing `!` forces GPG to use the primary key in the published trust anchor instead of automatically
selecting a signing subkey that has not been included in the repository public key.

An official version must produce and publish exactly four explicit Release assets: the archive, checksum, archive detached signature, and `sun.sh.asc`. The packager immediately verifies its signatures; official tags and `--release` reject `--sign off`.

After creating the archive, the packager revalidates release-source bytes and the exact HEAD/tag identity before signing, then revalidates again after signing and after acquiring an exclusive lock on the output directory. Concurrent packagers committing to the same directory are serialized. Ordinary errors attempt to restore the previous set; an incomplete rollback retains `.sun-commit-backup-*` evidence and makes later packaging fail closed pending manual recovery. The four independent paths are not one filesystem-atomic switch for unlocked readers, and `SIGKILL`, a kernel crash, or power loss can leave a partial set plus a recovery directory. Crash atomicity is not promised: read, verify, or upload `$release_dist` only after the command returns successfully and no recovery directory remains.

## Generated files

```text
$release_dist/security-update-notify-VERSION.tar.gz
$release_dist/security-update-notify-VERSION.tar.gz.sha256
$release_dist/security-update-notify-VERSION.tar.gz.asc  # signed build
$release_dist/sun.sh.asc                                  # signed build, high-assurance first install
```

The release archive contains only product files required for installation, diagnostics, bootstrapping, and migration compatibility, plus the user and maintainer guides referenced by the READMEs. Build tools, workflows, and private operations material are excluded. `sun.sh` is included in the signed archive; signed builds also create `sun.sh.asc` outside the archive so nondeterministic signature time never enters the reproducible tarball. The mirror extracts the script and key from the verified archive and publishes them with the detached signature in the immutable version directory; the compatibility stable URL still serves only `sun.sh`. `install.sh` and `files/security-update-notify` are generated by the Go packager as a minimal launcher and version marker for old 2.x self-upgrade clients. They contain no legacy installer/runtime logic and are never installed.

## Verify the Draft before immutable publication

Publication must follow this exact order. Continue using the variables from the verified release commit and
the local annotated tag that has not yet been pushed. Generate a non-empty `notes_file` from the one matching
CHANGELOG section; do not hand-edit a placeholder path:

```bash
set -euo pipefail
archive="security-update-notify-${tag#v}.tar.gz"
assets=("$archive" "$archive.sha256" "$archive.asc" "sun.sh.asc")
release_epoch="$(git show -s --format=%ct "$release_sha")"
notes_file="$(mktemp "/tmp/security-update-notify-${tag}-notes.XXXXXX")"
awk -v heading="## ${tag#v}" '
  $0 == heading { seen++; capture = (seen == 1); next }
  capture && /^## / { capture = 0 }
  capture { body[++count] = $0 }
  END {
    if (seen != 1) exit 1
    first = 1
    while (first <= count && body[first] == "") first++
    last = count
    while (last >= first && body[last] == "") last--
    if (last < first) exit 1
    for (line = first; line <= last; line++) print body[line]
  }
' CHANGELOG.md >"$notes_file"
[[ -s "$notes_file" ]]
```

Build the official assets directly into the fresh `$release_dist` created above; do not reuse the repository's
`dist/`, which may contain files from an older version. The function below requires exactly the four regular
files, independently checks the checksum, archive allowlist, and archive signature, and creates a fresh GPG home
on every call. It requires exactly one valid bootstrap signature outcome bound to both the pinned primary
fingerprint and one critical version notation:

```bash
set -euo pipefail
release_pin='C678256ACBFC6491BF5076655F3AE24999921FFC'
release_notation='release-version@xxv.cc'
verify_release_set() {
  local set_dir="$1" actual_set expected_set verify_work bootstrap_status
  local gpg_home
  local -a gpg_cmd primary_fingerprints

  actual_set="$(find "$set_dir" -mindepth 1 -maxdepth 1 \
    -printf '%f\t%y\n' | LC_ALL=C sort)"
  expected_set="$(printf '%s\tf\n' "${assets[@]}" | LC_ALL=C sort)"
  [[ "$actual_set" == "$expected_set" ]]

  (cd "$set_dir" && sha256sum -c "$archive.sha256")
  go run ./cmd/security-update-notify verify \
    --tarball "$set_dir/$archive" \
    --sha256 "$set_dir/$archive.sha256" \
    --asc "$set_dir/$archive.asc" \
    --pubkey files/release-signing.pub.asc \
    --fingerprint "$release_pin"
  python3 -I build/release-archive-test.py \
    "$set_dir/$archive" "${tag#v}" "$release_epoch" .

  verify_work="$(mktemp -d "/tmp/security-update-notify-${tag}-verify.XXXXXX")"
  gpg_home="$verify_work/gnupg"
  install -m 0700 -d "$gpg_home"
  tar -xOf "$set_dir/$archive" \
    "security-update-notify-${tag#v}/sun.sh" >"$verify_work/sun.sh"
  cmp sun.sh "$verify_work/sun.sh"
  gpg_cmd=(gpg --no-options --homedir "$gpg_home" --batch)
  "${gpg_cmd[@]}" --import files/release-signing.pub.asc
  mapfile -t primary_fingerprints < <(
    "${gpg_cmd[@]}" --with-colons --fingerprint --list-keys |
      awk -F: '$1 == "pub" { want = 1; next }
                want && $1 == "fpr" { print $10; want = 0 }'
  )
  [[ "${#primary_fingerprints[@]}" -eq 1 \
     && "${primary_fingerprints[0]}" == "$release_pin" ]]
  bootstrap_status="$("${gpg_cmd[@]}" \
    --known-notation "$release_notation" --status-fd=1 --show-notation \
    --verify "$set_dir/sun.sh.asc" "$verify_work/sun.sh" \
    2>"$verify_work/bootstrap-gpg.log")"
  awk -v pin="$release_pin" -v notation="$release_notation" \
      -v version="${tag#v}" '
    $1 == "[GNUPG:]" && $2 == "GOODSIG" { outcome_count++; good_count++ }
    $1 == "[GNUPG:]" && $2 ~ /^(EXPSIG|EXPKEYSIG|REVKEYSIG|BADSIG|ERRSIG)$/ {
      outcome_count++
    }
    $1 == "[GNUPG:]" && $2 == "VALIDSIG" {
      valid_count++
      if ($3 == pin || $NF == pin) pinned_count++
    }
    $1 == "[GNUPG:]" && $2 == "NOTATION_NAME" {
      name_count++
      if (NF == 3 && $3 == notation) name_match++
    }
    $1 == "[GNUPG:]" && $2 == "NOTATION_FLAGS" {
      flags_count++
      if (NF == 4 && $3 == 1 && $4 == 1) flags_match++
    }
    $1 == "[GNUPG:]" && $2 == "NOTATION_DATA" {
      data_count++
      if (NF == 3 && $3 == version) data_match++
    }
    END {
      exit !(outcome_count == 1 && good_count == 1 &&
             valid_count == 1 && pinned_count == 1 &&
             name_count == 1 && name_match == 1 &&
             flags_count == 1 && flags_match == 1 &&
             data_count == 1 && data_match == 1)
    }
  ' <<<"$bootstrap_status"
}

[[ "$(git cat-file -t "$tag")" == tag ]]
[[ "$(git rev-parse "$tag^{commit}")" == "$release_sha" ]]
verify_release_set "$release_dist"
```

Only after the local set passes may the tag be pushed. Immediately read both the direct and peeled refs from
the remote, require the remote object to equal the local annotated tag object, and require it to peel only to
`release_sha`. Do not treat `gh --verify-tag` as proof of annotated-tag identity:

```bash
set -euo pipefail
verify_remote_tag() {
  local remote_refs remote_tag_object remote_tag_commit
  remote_refs="$(git ls-remote origin "refs/tags/$tag" "refs/tags/$tag^{}")"
  remote_tag_object=''
  remote_tag_commit=''
  while read -r object ref; do
    case "$ref" in
      "refs/tags/$tag") remote_tag_object="$object" ;;
      "refs/tags/$tag^{}") remote_tag_commit="$object" ;;
    esac
  done <<<"$remote_refs"
  [[ "$remote_tag_object" == "$(git rev-parse "$tag")" ]]
  [[ "$remote_tag_commit" == "$release_sha" ]]
}
git push origin "refs/tags/$tag"
verify_remote_tag
```

Create a mutable Draft Release from that existing remote tag and upload the four explicitly listed assets:

```bash
set -euo pipefail
gh release create "$tag" \
  "$release_dist/$archive" \
  "$release_dist/$archive.sha256" \
  "$release_dist/$archive.asc" \
  "$release_dist/sun.sh.asc" \
  --draft --verify-tag \
  --repo xxvcc/security-update-notify \
  --title "$tag" --notes-file "$notes_file"
```

Omitting `--draft` publishes the Release too early; omitting `--verify-tag` lets `gh` create a lightweight tag when the remote tag is absent. Neither omission is allowed.

Download every Draft asset into a fresh directory. First use GitHub JSON metadata to prove that the Release is
still a Draft, the tag is correct, the asset-name set is exact, and the body is byte-identical to the extracted
CHANGELOG section. Then run the same signature/archive function on the downloaded set and byte-compare it with
the local signed set:

```bash
set -euo pipefail
verify_dir="$(mktemp -d)"
gh release download "$tag" --repo xxvcc/security-update-notify --dir "$verify_dir"
release_json="$verify_dir/release.json.part"
gh release view "$tag" --repo xxvcc/security-update-notify \
  --json assets,body,isDraft,tagName >"$release_json"
python3 -I - "$notes_file" "$release_json" "$tag" "${assets[@]}" <<'PY'
import json
import sys
from pathlib import Path

notes_path, json_path, expected_tag, *expected_assets = sys.argv[1:]
metadata = json.loads(Path(json_path).read_text(encoding="utf-8"))
actual_assets = sorted(asset["name"] for asset in metadata["assets"])
if metadata["isDraft"] is not True:
    raise SystemExit("release is no longer a Draft")
if metadata["tagName"] != expected_tag:
    raise SystemExit("Draft tag does not match the verified tag")
if actual_assets != sorted(expected_assets):
    raise SystemExit(
        f"Draft asset set mismatch: {actual_assets!r} != {sorted(expected_assets)!r}"
    )
expected_body = Path(notes_path).read_text(encoding="utf-8")
if not expected_body or metadata["body"] != expected_body:
    raise SystemExit("Draft body differs from the exact CHANGELOG entry")
PY
rm -f -- "$release_json"
verify_release_set "$verify_dir"
for asset in "${assets[@]}"; do
  cmp "$release_dist/$asset" "$verify_dir/$asset"
done
```

An upload success or the earlier local result is not remote verification. The associated tag remains mutable while
the Release is a Draft, so call `verify_remote_tag` again immediately before publication to close the full Draft
verification window. Only after every Draft check passes may it be published as an immutable Latest Release.
Immediately require the API to report that the Release is locked:

```bash
set -euo pipefail
verify_remote_tag
gh release edit "$tag" --draft=false --latest --verify-tag \
  --repo xxvcc/security-update-notify
release_immutable="$(gh api "repos/xxvcc/security-update-notify/releases/tags/$tag" \
  --jq .immutable)"
latest_tag="$(gh api repos/xxvcc/security-update-notify/releases/latest --jq .tag_name)"
[[ "$release_immutable" == true && "$latest_tag" == "$tag" ]]
```

## Publication and mirror protection

The `Mirror signed release` workflow starts after the unprivileged CI for an official GitHub Release completes; that CI is only an event signal and defense-in-depth check and cannot authorize deployment by itself. The actual deployment gate comes from the protected default-branch workflow revision. Its automatic path checks out the successful CI run's fixed `head_sha`, confirms that the tag still resolves to the same commit, and uses the GitHub compare API to prove that both the release commit and the executing workflow revision belong to the current protected `main` history. Manual repairs are also rejected in the repository workflow unless dispatched from `refs/heads/main`. The workflow's `verify-release` runner has no Environment. It first independently verifies the exact asset set, archive, all five ELF identities, and static linkage with the offline fingerprint and verifier fixed on the default branch. The checked-out tag source remains non-executed data, while each authenticated runtime is executed with `--version` in an empty environment with a fixed PATH, bounded timeout, and output limit. Only after that runner succeeds does a fresh `verify-and-sync` runner receive the GitHub Environment identity restricted to `main`; it revalidates asset structure, the canonical checksum, metadata, GPG, the archive, and bootstrap signature from scratch without executing any release payload.

The deployment SSH identity is constrained by forced-command `rrsync` and cannot execute arbitrary shell commands on the mirror host; it exists only in the Environment restricted to `main`. Repository-wide concurrency serializes all writes by `verify-and-sync`. The deployment runner extracts `sun.sh` and the public key from the verified archive, verifies the bootstrap signature and version notation, uploads the immutable version directory, and reads the complete versioned set back from `dl.ll.cd`; it then queries GitHub Latest again. Only while the target remains Latest does it update the stable `sun.sh` with a single-file `rsync --delay-updates` operation and public read-back, followed by a final update and read-back of `latest.json`. Manually rerunning an older release only repairs its version directory and cannot replace the stable bootstrap or Latest manifest.

`sun.sh` and `latest.json` are each delayed replacements, but the pair is not a cross-file transaction. If the stable script succeeds and a later step fails, the public endpoint can temporarily contain a new `sun.sh` with the old `latest.json`; update discovery remains on the old manifest, and the maintainer must idempotently rerun the same tag from `main`. Do not publish another official version until the previous mirror and canary finish: GitHub concurrency retains only one pending job, so a later release can replace a pending job that has not started and the displaced version must then be rerun manually. Repository Release immutability is enabled. After every successful mirror and each Monday, independent real GitHub-hosted Ubuntu 22.04/24.04 canaries redownload both public sources and exercise signature verification, installation, doctor, dry-run, timer state, uninstall, and APT-policy restoration.

The Release must first become immutable. After unprivileged release CI verifies the public assets, only the default-branch mirror workflow can use the Environment-scoped deployment identity; tag source is not executed, and authenticated runtimes are invoked only for real version probes. Never bypass checksum, GPG, pinned fingerprint, version notation, five-architecture execution, public read-back, or canary gates.

## Post-release verification

- GitHub Latest points to the target immutable Release, whose explicit asset set contains exactly four files.
- GitHub and versioned-mirror assets are byte-identical and pass checksum and GPG verification.
- Stable `sun.sh`, versioned `sun.sh`, and the signed archive copy match; the critical notation binds the target version.
- Ubuntu 22.04/24.04 public canaries complete install, doctor, dry-run, timer, uninstall, and APT baseline restoration.
- Finally confirm that `main`, its remote commit, the tag, and the published version are bound to the same source.
